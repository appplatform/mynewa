# ADR 0001 — 업무 규칙을 core 하나에 두고 RPC로 노출한다

- 상태: 채택 (2026-10-06)

## 맥락
메타 프롬프트 §4.2는 NestJS 모듈 구조를 권장했다. 하지만 이 서비스의 핵심 위험은 "정산·등급·법적 게이트 규칙이 여러 곳에서 조금씩 다르게 구현되는 것"이다. 또 사업자가 서버 없이도 흐름 전체를 확인할 수 있는 데모가 필요했다.

## 결정
- 모든 규칙을 프레임워크 없는 TypeScript 패키지 `@coco/core`에 둔다. 작업마다 zod 입력 스키마·인증 수준·역할을 선언한다.
- HTTP는 `POST /api/rpc/:op` 하나로 노출한다(Fastify). REST 리소스 설계는 외부 공개 API가 필요해질 때 별도 게이트웨이로 만든다.
- 브라우저 데모는 같은 core를 MemoryStore 위에서 실행한다.

## 결과
- 장점: 규칙이 한 곳에 있고, 테스트가 HTTP 없이 빠르다(core 34개 테스트 < 1초). 데모와 서버의 동작이 일치한다.
- 단점: 엔드포인트 단위 캐싱·문서화가 REST보다 불편하다. `GET /api/ops`로 작업 목록을 노출해 보완한다.
- NestJS 대신 Fastify를 쓴 이유: RPC 단일 진입점에는 DI 컨테이너가 필요 없고, 의존성이 적을수록 감사 범위가 줄어든다.
